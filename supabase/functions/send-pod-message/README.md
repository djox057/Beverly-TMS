# POD preview and message

Manual action for accounting, manager, and admin on Loads, BG Loads, LALE Loads, and UES Loads. Opening a row loads current POD records and signed previews; sending attaches the selected original documents and the user's message. Images and PDFs are supported. A sole POD is selected automatically; multiple PODs require explicit selection. Rejections are saved in `pod_rejections`; original documents are unchanged.

| Operation | Input | Result | Authentication |
| --- | --- | --- | --- |
| POST `send-pod-message`, action `preview` | `orderId` | Load number, signed POD URLs, To and Reply-To, or a recipient error | Valid user JWT plus an allowed database role |
| POST `send-pod-message`, action `send` | `orderId`, `message`, `selectedFileIds`, `requestId` | Resend email ID after acceptance | Same checks; user-scoped order and document reads |
| POST `send-pod-message`, action `delete-rejection` | `rejectionId` | Hide the accessible report with deletion time and actor; original documents stay intact | Valid user JWT and allowed database role, then a user-scoped report lookup |
| POST Resend `/emails` | Server-resolved addresses, message, original attachments | Provider email ID | Existing server-only `RESEND_API_KEY` |

Recipient matching uses `orders.booked_by` as an exact profile name or user ID. The manager is the unique manager-role profile in the booker's office. No match, duplicate match, absent office, or missing Auth email blocks sending and displays a reason. To uses the booker's Auth email; Reply-To uses the signed-in sender's Auth email and the manager's Auth email. No client-supplied recipient, storage path, attachment content, or role is trusted.

Only `order_files` records with the requested `order_id` and `file_category = POD` can be attached. RLS is preserved on order, file, role, and storage reads. After authorization, the service client resolves Auth email addresses and writes server-validated rejection reports; clients have read-only access to this history. Email HTML is escaped. Attachment limits are 20 documents and 25 MB of actual bytes (below Resend's 40 MB encoded limit). Requests time out after 30 seconds; the UI preserves the draft on failure and retries the same unchanged payload with the same Resend idempotency key. Idempotency lasts 24 hours per Resend documentation. Success means provider acceptance, not inbox delivery.

Provider documentation: https://resend.com/docs/api-reference/emails/send-email and https://supabase.com/docs/guides/functions/auth-legacy-jwt.

Validation: UI navigation/selection/role tests, server recipient and attachment rules, and mocked endpoint tests exercising authorization, forged recipients, foreign load documents, actual attachment size, missing files, and provider failures. Production manager mappings and POD content types were checked read-only. No test email was sent to staff. Apply the rejection-history migration and deploy this endpoint with JWT verification enabled before publishing the UI. The history contains broker load number, booking dispatcher name, selected document snapshots, reason, reporter identity/name, and email notification state. The list has a confirmed delete action for accounting, manager, and admin. Deletion markers hide the report while retaining request IDs, so retries cannot recreate it. Dispatcher names are backfilled for existing reports. Reports are saved before emailing and deduplicated per caller/order/request ID. A failed email retains the rejection with an unconfirmed-notification indicator. Earlier messages are not backfilled because they were not stored. Each page filters history by its booked-by company scope and loads 50 reports per page only when opened. Roll back the UI commit and restore the previous email endpoint together, keeping the history table and existing reports. No background jobs or automatic sends are installed.
